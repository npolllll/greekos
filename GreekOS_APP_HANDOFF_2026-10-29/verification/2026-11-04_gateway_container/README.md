# Голосовой шлюз в отдельном контейнере — проверка облачного пути (04.11.2026, 21:31 UTC)

**Что это доказывает.** Голосовой шлюз (`voice-gateway/server.ts`) собирается в production-контейнер
(`voice-gateway/Dockerfile`, тот же образ, что разворачивается на Fly.io через `voice-gateway/fly.toml`)
и в режиме `APP_ENV=production` проводит полный разговор по облачным протоколам:
распознавание Azure (REST short audio) → Claude (Anthropic Messages, потоковый ответ) → синтез Azure
по фразам → звук в браузер, с перебиванием, сохранением реплик и итогами.

**Чего это НЕ доказывает.** Провайдеры здесь — локальный сервер, говорящий по протоколам Azure Speech
и Anthropic (`provider-mock` в рабочей папке сессии): он отвечает мгновенно и одним и тем же текстом.
Это не живой API и не финальная приёмка. Качество греческой речи, естественность голосов, точность
распознавания и реальная задержка провайдеров здесь не измерены — для этого нужны ключи владельца
(см. `docs/PRODUCT_STATUS.md`). После развёртывания та же проверка запускается против живых сервисов:
шаг 10 `scripts/deploy-cloud.sh` (`scripts/voice-smoke.ts --gateway wss://…fly.dev`).

## Как запускалось

- Образ: `docker build -f voice-gateway/Dockerfile -t greekos-voice:local .` (база `node:22-bookworm-slim`,
  только production-зависимости, пользователь `node`, проверка `/health`).
- Контейнер: `APP_ENV=production`, `LLM_PROVIDER=anthropic`, `ASR_PROVIDER=azure`, `TTS_PROVIDER=azure`,
  адреса Anthropic/Azure направлены на локальный сервер протоколов, база — локальный Supabase.
- Клиент: `scripts/voice-smoke.ts --turns 4` — временный тестовый аккаунт (`dev_preview_tester`;
  только такому аккаунту рабочий шлюз разрешает синтетический вход), сценарий SC05 (кафе),
  4 реплики ученика, перебивание на 2-й реплике, завершение с итогами, затем аккаунт удаляется.
- Для звука ответа роли `TUTOR_F` на время проверки был назначен и утверждён облачный голос
  (в рабочей версии без утверждения владельцем ответ идёт только текстом — так и задумано);
  после проверки кастинг восстановлен из снимка, тестовые записи расходов удалены.

Разбор задержки одной реплики: ожидание тишины после конца речи (VAD, уровень начинающего) ≈ 1300 мс,
распознавание ≈ 15 мс, первая фраза модели ≈ 10 мс, первый звук синтеза ≈ 55 мс. То есть при
мгновенных провайдерах **накладные расходы самого шлюза ≈ 60 мс**, а нижнюю границу задаёт пауза
конца реплики. Кнопка «Готово» завершает реплику сразу, без этой паузы. Реальная задержка в облаке
= 1,3 с + распознавание Azure + первая фраза Claude + первый звук Azure; её замер — после подключения
ключей.

## Поправки к файлам

- Поле `providers` в `voice-smoke-cloud-protocols.json` записано по окружению машины, **запускавшей
  тест**, а не шлюза: там стоит `llm: openai_compatible`. Шлюз работал с `LLM_PROVIDER=anthropic` —
  это видно по `provider-calls.json` (`POST /v1/messages` — протокол Anthropic Messages). Ошибка
  исправлена: `/health` шлюза теперь сообщает имена его провайдеров (без ключей), а отчёт пишет их
  в поле `gateway_providers`.
- В `voice-smoke-cloud-protocols.json` поле `recognized` не совпадает с `learner`: локальный сервер
  протоколов возвращает фразы по кругу, а не распознаёт звук. Это свойство заглушки, не шлюза.
- `provider-calls.json` — счётчик вызовов за все прогоны против этого сервера (настроечные и итоговый), а не за один.

## Где это работает в облаке

Vercel не держит долгие WebSocket-соединения, поэтому шлюз — отдельный сервис. Выбран Fly.io:
один постоянно работающий экземпляр (512 МБ, `auto_stop_machines = "off"`) во Франкфурте рядом с
Supabase EU и Azure westeurope, HTTPS/WSS и проверка `/health` из коробки, развёртывание тем же
`Dockerfile`. Для 4–5 учеников одного экземпляра достаточно; шлюз держит соединения в памяти,
пингует их каждые 15 с и закрывает неотвечающие. Распознавание и синтез идут из шлюза в Azure по
REST, модель — в Anthropic по HTTPS; браузер соединяется только со шлюзом (`NEXT_PUBLIC_VOICE_GATEWAY_URL`)
по одноразовому подписанному токену, выданному приложением (`VOICE_GATEWAY_SECRET`).
